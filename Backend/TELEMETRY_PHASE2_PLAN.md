# Feature 2.4 — Distributed Telemetry & Observability — Implementation Plan

> Seventh implementation plan, after `RESTAURANTS_PHASE1_PLAN.md`, `ORDERS_PHASE1_PLAN.md`, `NOTIFICATIONS_PHASE1_PLAN.md`, `DELIVERY_PHASE2_PLAN.md`, `REALTIME_PHASE2_PLAN.md` and `CACHING_PHASE2_PLAN.md`. This one covers **Feature 2.4 — Distributed Telemetry & Observability**, the fourth feature of **Phase 2** in `FoodDelivery_ProjectPlan.md`.

> **Status: Milestones A (2026-07-31, see §2), B (2026-07-31, see §3), C (2026-07-30, see §4), D (2026-08-01, see §5), E (2026-08-02, see §6) and G (2026-08-04, see §8) shipped — only the optional F remains (§1).** **G (§8) was added 2026-08-01, after D shipped:** D correlates the synchronous request only, and the outbox/inbox tables break both the trace and the correlation id, so the asynchronous half of every cross-service flow was still uncorrelated. It was not previously in this plan or in its out-of-scope list. The paragraph below records the state this plan was verified against before any of them landed — its health-check rows are superseded by §4, its "no metrics anywhere" claim by §2 and §3, and its correlation rows by §5.
>
> **Status (verified against the code on 2026-07-28, before Milestone C): not started.** No `.WithMetrics()`, no `Meter` anywhere in the solution, health checks still single-and-untagged on all eight hosts, no collector/Prometheus/Grafana in `docker-compose.yml`. Everything below is open work. Two later plans have since been written and both consume this one: `KUBERNETES_PHASE2_PLAN.md` (2.5) binds pod probes to Milestone C's `/health/live` + `/health/ready` and runs Milestone E's collector stack in-cluster; `REVIEWS_PHASE2_PLAN.md` (2.6) expects the probe convention to exist when it stands up a new service. Milestone C is therefore the highest-leverage part of this plan for everything downstream — **it can and should land first**, since it depends on nothing here.

> **Scope for this iteration:** complete the three pillars of observability across every service. Tracing is already shipped (OTLP → Jaeger); this feature (1) turns on the **metrics** pillar that is entirely missing today, centralised in `AddInfrastructure` so every host gets it, plus a shared meter/activity-source helper; (2) adds **RED + business metrics** through the MediatR pipeline and a first set of real domain metrics (orders placed, state transitions, assignment latency); (3) splits the single untagged `/health` into **liveness vs readiness** endpoints that Feature 2.5 (Kubernetes) will wire to pod probes; (4) completes **trace ↔ log correlation** (SpanId + business ids in the log scope) and stamps a **gateway correlation id**; (5) stands up a **local metrics backend + dashboards + alerts** (OpenTelemetry Collector → Prometheus + Grafana, dashboards-as-code) so the hit-rate / RED / orders-per-minute story is visible; and (6) optionally swaps the backend for **Azure Monitor / Application Insights** behind config. Each milestone is independently shippable, unit- **and** integration-tested (in-process `MetricCollector` / in-memory OTel exporter, plus Testcontainers for health), and sized for a single PR review.

> **Sequencing:** the prerequisites are met. **`REALTIME_PHASE2_PLAN.md` (2.2) shipped A–D** (dedicated RealTime host on `:5600`, `RealTimeDiagnostics` activity source, Postgres + Redis + RabbitMQ + Duende health checks) and **`CACHING_PHASE2_PLAN.md` (2.3) shipped A–D** (cache-aside helper, `ICachedQuery`/`QueryCachingBehavior`, menu-key eviction, `IDistributedLock`). Both add surfaces this feature instruments. **Caching Milestone E was the one exception — written up as shipped on 2026-07-28 with no code behind it, then actually built on 2026-07-29; `CacheDiagnostics` now exists and Milestone A only had to register its meter (see §11).** §11 records the full reconciliation so nothing is instrumented twice and the metrics pipeline is owned in exactly one place. This plan runs **before** Feature 2.5 (AKS) and Feature 2.6 (Reviews), both of which consume its liveness/readiness probes.

Decisions locked in for this plan:

- **Build on the OTLP substrate that already exists — do not fork the telemetry config.** Tracing is wired centrally in `AddInfrastructure` (`Common.Infrastructure/InfrastructureConfiguration.cs`): ASP.NET Core, HttpClient, EF Core, Npgsql, Redis and MassTransit sources, OTLP-exported to Jaeger. This feature **adds `.WithMetrics()` and completes `.WithLogging()`/correlation on the same `AddOpenTelemetry()` builder**, so a service opts into nothing — it gets all three pillars from the one `AddInfrastructure` call it already makes. No parallel telemetry stack. *(Shipped in A, with one refinement: the builder's host-agnostic half moved into `Common.Presentation`'s `AddHostTelemetry` so the Gateway and Identity share it instead of copying it — `AddInfrastructure` calls that and adds the module sources and meters.)*
- **Local-first, offline-testable backends; Azure is the optional final swap.** The project-plan text names Azure Monitor / Application Insights, but the running stack is **Jaeger + Seq** (local, in `docker-compose`, available as Testcontainers). Consistent with the Caching and Real-Time plans, every milestone here targets **OTLP + local backends** (metrics land in Prometheus + Grafana via an OpenTelemetry Collector; traces stay in Jaeger; logs stay in Seq) so the whole feature is testable with `docker-compose up` and in CI. **Azure Monitor / App Insights is Milestone F** — a config-selected exporter swap, same instrumentation, mirroring `CACHING_PHASE2_PLAN.md` §7 and `REALTIME_PHASE2_PLAN.md` §6.
- **Metrics are recorded declaratively at the pipeline boundary, not by hand in each handler.** The codebase already composes four MediatR behaviors in `Common.Application/ApplicationConfiguration.AddApplication` — ExceptionHandling → RequestLogging → Validation → **QueryCaching** (2.3 shipped the fourth). We add a `RequestMetricsBehavior` that records a **RED** signal (request count, duration histogram, failure count from the `Result`) tagged by request name — so every command/query is measured without touching a handler. Genuine **business** metrics (`orders.placed`, order state transitions, assignment outcome/latency) are a handful of explicit counters emitted from the existing domain-event handlers / the one place that already owns that operation — never new domain logic.
- **Promote the *two* one-off diagnostics classes into a shared helper.** There are now two byte-for-byte-identical copies of the same idea: `Delivery.Infrastructure/Locations/DeliveryDiagnostics.cs` (`FoodDeliveryService.Delivery`, nearest-driver geo span) and `RealTime.Infrastructure/RealTime/RealTimeDiagnostics.cs` (`FoodDeliveryService.RealTime`, Redis pub/sub location forward, added by 2.2 Milestone C) — each a `public static class` with a `SourceName` const and a static `ActivitySource`, each registered by a hand-written `AddSource(...)` line in its own host. Two copies is the duplication signal the helper exists to remove. This feature generalises them into a small `Common.Infrastructure/Diagnostics` convention — a holder for a module's `ActivitySource` **and** its `Meter`, plus a registration extension — so custom spans and custom metrics are declared and wired the same way everywhere. *(Shipped in A as `AppDiagnostics` + `AddModuleDiagnostics`, composed rather than inherited so the two call sites kept their `{Module}Diagnostics.ActivitySource` shape. Note the meters are registered by the **host's** one-line `AddModuleDiagnostics` call, not auto-discovered by `AddInfrastructure` — nothing can enumerate a module's static holders for it.)*
- **Health checks already exist per service — this feature makes them probe-shaped.** Seven of the eight hosts map a single untagged `GET /health`; six of those check Npgsql + Redis + RabbitMQ + Duende, Identity checks Npgsql only, and the **Gateway has no health check at all**. Feature 2.5 needs the standard **liveness** (process is up — never fail on a dependency) vs **readiness** (dependencies reachable — pull the pod from rotation when not) split. Milestone C introduces tagged checks and `/health/live` + `/health/ready`, centralised in a shared mapping extension, keeping `/health` as the aggregate for back-compat. This is the explicit hand-off to `FoodDelivery_ProjectPlan.md` Feature 2.5 ("liveness and readiness probes using the health check endpoints from Feature 2.4"), and to 2.6's new Reviews host.
- **Two hosts do NOT call `AddInfrastructure` — the Gateway *and* Identity.** `Gateway/Program.cs` wires OTel tracing by hand (with the `Yarp.ReverseProxy` source) and has **no health check and no metrics**. `FoodDeliveryService.Identity` is worse off: it has Serilog + a single Npgsql health check and **no OpenTelemetry at all** — no `DiagnosticsConfig`, no tracer, no `UseLogContext()`. So the token endpoint — on the critical path of literally every authenticated request — is a hole in every Jaeger trace and in every Seq correlation today. Wherever this plan says "centralise in `AddInfrastructure`", the same wiring is exposed as a small standalone extension **both** hosts call, so the proxy hop and the identity hop show up in traces, metrics and health.
- **Correlation is completed, not reinvented.** W3C `traceparent` already propagates across HTTP and RabbitMQ (OTel), and `LogContextTraceLoggingMiddleware` pushes `TraceId` into Serilog. Milestone D adds `SpanId` + `service.name` + the relevant business id (OrderId/DriverId) to the log scope and has the **gateway stamp an `X-Correlation-Id`** (defaulting to the trace id) so a support agent has one id that ties Seq logs to a Jaeger trace. No new id scheme competes with the trace id. *(Shipped in D as one `UseRequestCorrelation()` in `Common.Presentation/Correlation`, replacing the seven per-host copies and giving Identity its first log correlation — see §5.)*
- Reference implementations to mirror: **`InfrastructureConfiguration.AddInfrastructure`** for the central OTel builder; **`DeliveryDiagnostics`** for the source/meter shape; the **`Common.Application/Behaviors`** pipeline for where `RequestMetricsBehavior` slots in; the **host `Program.cs`** health-check block for the liveness/readiness split; and the **Restaurants/Orders/Delivery integration suites** (`IntegrationTestWebAppFactory` + Testcontainers + real Duende JWTs) for driving endpoints while asserting telemetry.

## 2. Milestone A — Metrics pillar on + shared diagnostics helper (Common)

> **Status: shipped 2026-07-31.** All eight hosts now emit metrics; Identity emits telemetry of any kind for the first time. Build clean (0 warnings); `Common.UnitTests` 43/43 (5 new) and `Orders.IntegrationTests` 19/19 (3 new) green.
>
> **What was built, and where it differs from the tasks below:**
> - **`Common.Presentation/Telemetry/HostTelemetryExtensions.AddHostTelemetry(serviceName, exportLogsViaOtlp)`** — the resource, ASP.NET Core + HttpClient tracing, ASP.NET Core + HttpClient + runtime + process metrics, and the OTLP exporter on both pillars. It lives in **`Common.Presentation`, not `Common.Infrastructure`** — the same call the Gateway and Identity need, and Milestone C had already established that neither of those takes a `Common.Infrastructure` dependency. `AddInfrastructure` therefore *calls* it (a new `Common.Infrastructure` → `Common.Presentation` project reference) and layers the module-only sources on top, so the baseline has exactly one definition instead of the three it was heading for.
> - **`AddInfrastructure`** keeps EF Core / Redis / Npgsql / MassTransit tracing and adds the matching meters: `Npgsql`, MassTransit's `InstrumentationOptions.MeterName`, and `CacheDiagnostics.MeterName`. MassTransit's meter is one line beyond the task list and symmetric with the source that was already registered.
> - **`Common.Infrastructure/Diagnostics/`** *(`AppDiagnostics` moved to `Common.Application/Diagnostics` in Milestone B — see §3; `AddModuleDiagnostics` stayed)* — `AppDiagnostics` (a sealed class holding `Name` + `ActivitySource` + `Meter`) and `AddModuleDiagnostics(params string[] names)`, which calls `AddSource` **and** `AddMeter`. `AppDiagnostics` is **composed, not inherited**: `DeliveryDiagnostics`/`RealTimeDiagnostics` stay `public static` holders (the shape `CacheDiagnostics` already had, and the shape their call sites want) with a private `AppDiagnostics` field behind `ActivitySource`/`Meter` properties. A base class would have forced every call site onto `.Instance.`; the plan's "(or paired statics)" allowance is what was taken. Their `SourceName` const is renamed **`Name`** — it names a meter now too.
> - **The cache counters were already there.** `CacheDiagnostics` was rebuilt for real on 2026-07-29, after §11 below was written. A built nothing there beyond `AddMeter(CacheDiagnostics.MeterName)`; see the corrected §11.
> - **Gateway** dropped its hand-rolled `AddOpenTelemetry()` block for `AddHostTelemetry` + the YARP source **and** the YARP meter (forwarding metrics the module hosts can't account for), and shed three now-transitive package references. **Identity** got `OpenTelemetry/DiagnosticsConfig.cs`, the `AddHostTelemetry` call and an `OTEL_EXPORTER_OTLP_ENDPOINT` key in both its appsettings files — it had neither before.
> - **Logs pillar:** wired as `exportLogsViaOtlp`, a parameter on both `AddHostTelemetry` and `AddInfrastructure`, defaulting to `false`. Deliberately **not** bound to a config key in any host: nothing receives OTLP logs until Milestone E's collector, and a config key that no backend reads is a promise the tree can't keep. E flips it.
> - **Tests** use `OpenTelemetry.Exporter.InMemory` rather than `MetricCollector<T>` from `Microsoft.Extensions.Diagnostics.Testing`. `MetricCollector` listens to a `Meter` directly, so it passes whether or not the instrument was ever registered with a provider — which is the entire thing this milestone had to prove. The integration tests attach a second in-memory reader to the real host's `MeterProvider` (`IntegrationTestWebAppFactory.CollectMetrics()`) and assert what it actually exports. `Microsoft.Extensions.Diagnostics.Testing` was therefore not added; Milestone B can still use it for pure emission assertions.
>
> - **Fixed in passing: the Gateway and Identity Dockerfiles could not build.** Milestone C gave both hosts a `Common.Presentation` project reference but never added the matching `COPY` lines, so their `dotnet restore` step — which runs before `COPY . .` — failed on a missing csproj. Every module Dockerfile copies each referenced csproj; those two did not. Both now copy `Common.Presentation` + `Common.Domain`, and both images were built to verify. Nothing in compose would have picked up this milestone's Gateway/Identity telemetry otherwise.
>
> Two findings worth carrying forward: **(1)** `OpenTelemetry.Instrumentation.Process` has never had a stable release — it is pinned at `1.16.0-rc.1` to match the 1.16.0 core, alongside the EF Core and Redis instrumentation packages that were already pre-release. **(2)** Resolving `TracerProvider`/`MeterProvider` from DI is what starts the listeners; outside a hosted app nothing else forces the build, so a test that records before resolving them silently observes nothing. Both diagnostics unit tests failed exactly that way first.

**Goal:** every service emits metrics from the same `AddInfrastructure` call it already makes, and there is one blessed way to declare a custom span or metric.

**Tasks:**
- Extend the existing `AddOpenTelemetry()` builder in `InfrastructureConfiguration` with `.WithMetrics(...)`:
  - built-in instrumentation: `AddAspNetCoreInstrumentation()`, `AddHttpClientInstrumentation()`, `AddRuntimeInstrumentation()` (GC, threadpool, exceptions), `AddProcessInstrumentation()`, and the Npgsql meter (`AddMeter("Npgsql")`). These give the RED/host baseline for free.
  - exporter: `AddOtlpExporter()` (metrics reader) — same OTLP endpoint the traces already use, so no new config key.
- Complete the **logs** pillar on the same builder (optional but cheap): add `.WithLogging()` / `AddOpenTelemetry()` logging so log records can also ride OTLP where a backend wants them — but **keep Serilog + Seq as the primary log path** (it already carries the correlation; do not rip it out). Gate the OTel log exporter behind config so Seq stays the default.
- Add a small `Common.Infrastructure/Diagnostics/AppDiagnostics` convention — a base (or paired statics) exposing a module's `ActivitySource` **and** `Meter` under a single service name, plus `IServiceCollection.AddModuleDiagnostics(name)` that calls `AddSource(name)` **and** `AddMeter(name)` on both providers. **Refactor both existing consumers onto it** — `DeliveryDiagnostics` (`FoodDeliveryService.Delivery`) and `RealTimeDiagnostics` (`FoodDeliveryService.RealTime`) — and replace the manual `AddSource(...)` lines in `Delivery.Api/Program.cs` and `RealTime.Api/Program.cs` with the shared call. Two identical classes collapsing into one convention is the proof the helper earns its keep, and it means custom meters are auto-registered (they are not today).
- ~~**Add the cache hit/miss counters here.**~~ **Superseded — Caching 2.3 Milestone E built them for real on 2026-07-29**, after this task was written against a tree where they did not exist (§11). `CacheDiagnostics` (`Common.Infrastructure/Caching`) owns the `FoodDeliveryService.Cache` meter with `cache.hits`/`cache.misses` (`Counter<long>`, unit `{lookup}`, tagged `cache.key_prefix` — prefix only, never the full key), recorded in `CacheService.GetAsync`. All this milestone owes them is `AddMeter(CacheDiagnostics.MeterName)` on the reader it stands up, plus the integration test proving they are now collected rather than dropped.
- Expose the metrics/OTel wiring the two non-`AddInfrastructure` hosts need as a standalone extension (`AddHostTelemetry(serviceName)` — resource + AspNetCore/HttpClient/runtime/process instrumentation + OTLP, no EF/Npgsql/MassTransit), and call it from **`Gateway/Program.cs`** (replacing its hand-rolled `AddOpenTelemetry()` block, keeping the `Yarp.ReverseProxy` source) and from **`Identity/Program.cs`** (which has no OTel today — this gives the token endpoint its first spans and metrics, and it needs a `DiagnosticsConfig.ServiceName` of its own, matching the other hosts' `OpenTelemetry/` folder convention).

**Unit tests** (`Common.UnitTests` — sits at `src/Common/FoodDeliveryService.Common.UnitTests`, already has `Behaviors/`, `Caching/`, `Locking/` folders; add `Diagnostics/AppDiagnosticsTests`):
- `AddModuleDiagnostics(name)` registers the source **and** the meter (assert both providers see the name);
- a `Meter`/counter created through the helper carries the expected instrument name + unit;
- an `ActivitySource` created through the helper produces a listened-to `Activity` (in-memory `ActivityListener`).

**Integration test** (reuse an existing suite, e.g. Orders, with the real host): drive one existing endpoint through the pipeline and, via `MetricCollector<T>` from `Microsoft.Extensions.Diagnostics.Testing`, assert the built-in `http.server.request.duration` histogram recorded a measurement; assert a smoke counter emitted through `AddModuleDiagnostics` is observable. (No metrics backend needed — collection is in-process.)

**Done when:** `.WithMetrics()` ships in `AddInfrastructure`, `DeliveryDiagnostics` **and** `RealTimeDiagnostics` are on the shared helper with their meters auto-registered, `cache.hits`/`cache.misses` are emitted **and collected**, the Gateway and Identity hosts both emit metrics (and Identity emits traces for the first time), all existing suites stay green.

## 3. Milestone B — RED + business metrics through the pipeline

> **Status: shipped 2026-07-31.** Every command and query now emits RED at the application boundary, and the first business counters fire on the real order and assignment flows. Build clean (0 warnings); `Common.UnitTests` 48/48 (5 new), `Orders.UnitTests` 25/25, `Delivery.UnitTests` 68/68, `Orders.IntegrationTests` 21/21 (2 new), `Delivery.IntegrationTests` 43/43 (1 new), and the Restaurants/Users/Notifications/RealTime integration suites (35/8/5/17) re-run green because the new behavior sits in every host's pipeline.
>
> **What was built, and where it differs from the tasks below:**
> - **`AppDiagnostics` moved from `Common.Infrastructure/Diagnostics` to `Common.Application/Diagnostics`.** This was forced, not preference: the code that owns a business measurement is a *handler*, and neither `Orders.Application` nor `Common.Application` may reference `Common.Infrastructure`. The type is pure BCL (`ActivitySource` + `Meter`), so nothing about the move touches OpenTelemetry; `AddModuleDiagnostics`, which does touch the providers, stays in `Common.Infrastructure`. > **Status: shipped 2026-08-01.** All eight hosts share one `app.UseRequestCorrelation()` (`Common.Presentation/Correlation`); the seven per-host middleware copies are deleted and Identity has log correlation for the first time. >
> **What was built, and where it differs from the tasks below:**
> - **The middleware moved to `Common.Presentation/Correlation`, not `Common.Infrastructure`** — the same reason `MapHealthProbes` and `AddHostTelemetry` live there: the Gateway and Identity need it and take no `Common.Infrastructure` dependency. Seven `LogContextTraceLoggingMiddleware.cs` copies and their seven `MiddlewareExtensions.cs` are gone (the Gateway's `Middleware/` folder with them); the module hosts keep that folder only for `GlobalExceptionHandler`.
> - **The extension is `UseRequestCorrelation()`, not `UseLogContext()`.** The call now stamps a response header as well as a log scope, so the old name actively misdescribed it. Eight `Program.cs` files, `CLAUDE.md`, `.claude/rules/presentation-messaging.md`, the `add-module` skill and `REVIEWS_PHASE2_PLAN.md` §host-bootstrap were updated to the new name — 2.6 copies that bootstrap verbatim.
> - **Two middlewares, one call.** `CorrelationIdMiddleware` owns the header contract; `LogContextTraceLoggingMiddleware` owns the Serilog scope and reads the id the first one parked in `HttpContext.Items`. Splitting them keeps "what the client sees" testable apart from "what Seq sees", and the ordering between them is fixed in the one extension rather than in eight pipelines.
> - **Fixed in passing: every one of the seven copies leaked its scope.** They did `return next.Invoke(context)` from *inside* the `using`, which disposes the `LogContext` push as soon as the first await yields — so `TraceId` covered only the synchronous head of the pipeline and was missing from exactly the handler logs worth correlating. The shared version awaits inside the scope, and `Invoke_Should_KeepTheScopeOpenAcrossAnAwait` pins it.
> - **`ServiceName` comes from DI, not a second constant.** `AddHostTelemetry` now also registers `HostServiceName` (the value it puts on the OTel resource), and the middleware takes it from there, so a log's `service.name` and its span's `service.name` cannot drift when a host is renamed. `UseRequestCorrelation` falls back to `IHostEnvironment.ApplicationName` for a host that somehow wants correlation without telemetry.
> - **No YARP transform was needed.** The Gateway middleware writes the resolved id back onto the **request** headers before `MapReverseProxy`, and YARP copies request headers to the proxied call by default — so the downstream service receives it, `IsWellFormed` accepts it and preserves it. One less piece of configuration to keep in step with the header name.
> - **Inbound ids are sanitised, not trusted.** The value is echoed into a response header and onto every log line, so anything outside `[A-Za-z0-9-_.:]` or longer than 128 characters (a header sent twice arrives comma-joined; CRLF is a response-splitting attempt) is **replaced by a generated id rather than rejected** — a malformed correlation header is not a reason to fail a customer's request.
> - **The response header is written from `OnStarting`.** Setting it inline would lose it on exactly the responses whose id someone wants: `GlobalExceptionHandler` resets the response when it writes ProblemDetails.
> - **Business ids come from the route, and the bare `id` is qualified.** Six of the eight endpoints that carry an aggregate id call the parameter `id`, so a literal reading would have every module logging an unsearchable `Id`. `BusinessIdRouteValues` reads the route *pattern*'s last literal segment before the parameter and singularises it — `orders/{id}/cancel` → `OrderId`, `delivery/drivers/{id}` → `DriverId`, `delivery/deliveries/{id}` → `DeliveryId` — while a self-naming parameter (`restaurantId`) is taken as it stands. Ids that exist only in the request body (`POST orders`) are deliberately not covered: reading the body in a middleware to enrich a log would buffer every payload in the system.
> - **`exportLogsViaOtlp` is untouched.** Seq stays the primary log path, exactly as A left it; E flips the switch when the collector exists.
>
> **Deviations from the test plan, and why:**
> - The unit tests needed a **recording `IHttpResponseFeature`**: `DefaultHttpContext` silently drops `OnStarting` callbacks, so the echoed header is untestable without one (or without a full server). ~25 lines inside the test class.
> - The integration log assertion needed a **replaced `ILoggerFactory`**. Serilog builds its logger once, inside the `ILoggerFactory` registration `UseSerilog` adds, so there is no hook to attach a sink to a host after it is built; `IntegrationTestWebAppFactory` registers a `SerilogLoggerProvider` writing to an in-memory sink with the same `Enrich.FromLogContext()` production uses. That is what makes the matched endpoint and its route values available to correlation middleware placed anywhere in `Program.cs` — a host that ever calls `UseRouting()` by hand after this call would silently lose the business ids.

## 8. Milestone G — Correlation across the outbox/inbox boundary

> **Status: shipped 2026-08-04.** Build clean; whole suite green — `Common.UnitTests` 110/110 (13 new) and `Orders.IntegrationTests` 31/31 (5 new), with the other eleven projects unchanged and passing (448 tests overall).
>
> **What was built, and where it differs from the tasks below:**
> - **`CorrelationContext` is ambient, not DI-scoped.** The plan said "scoped"; a scoped service is wrong here and the publish filter is why. `IEventBus` is a singleton over MassTransit's `IBus`, so a publish filter runs in a DI scope of MassTransit's own making with no relationship to the scope the publishing handler was resolved from — a scoped context reads back empty on exactly the leg this milestone exists to cover. The state is therefore an `AsyncLocal` **instance** field on a singleton: ambient like `Activity.Current` and `LogContext`, the two things it sits between, but still injected rather than static, so consumers declare the dependency and two hosts in one process (the integration tests) do not share a slot.
> - **The restore helper opens from the row, before deserialization** (`MessageDispatchScope.Begin(context, operation, messageType, correlationId, traceParent)`), with the message's business ids pushed separately afterwards (`PushBusinessIds`). Opening it around the deserialized event instead would have left the `catch`'s "exception while processing message" line — the one line anybody goes looking for — written just *outside* the scope.
> - **One task the plan did not list, and the milestone is hollow without it: the jobs now log per message.** `ProcessOutboxJob`/`ProcessInboxJob` logged twice per *batch* and nothing per *message*, so restoring a correlation id into a scope that produced no Seq line would have satisfied every assertion here and answered no support question at all. Each job now writes one `Dispatching {MessageType}` line inside the restored scope, carrying the id, the dispatch trace and the event's own `OrderId`.
> - **A `ParentSpanId` bug the unit test could not have caught.** `ActivitySource.StartActivity(name, kind, parentContext: default, …)` does **not** produce a root span: .NET reads a default `ActivityContext` as "no parent *given*" and falls back to `Activity.Current` — inside the job loop, the Npgsql span of the batch `SELECT`. The dispatch was silently parented to a database read; the unit test passed only because `Activity.Current` happened to be null there, and the real host caught it. `Activity.Current` is now cleared before the call and restored on dispose, and both halves are pinned by tests.
> - **The `correlation_id` column carries a partial index** (`WHERE correlation_id IS NOT NULL`) in all 11 tables. "Which outbox rows belong to this correlation id?" is the whole reason the id is a column instead of a field inside `content`, and it should not be a table scan.
> - **Truncation, not rejection**, on both columns (`MessageCorrelationColumns.FitCorrelationId`/`FitTraceParent`): an oversized id must never fail the business transaction it is only describing, nor the inbox insert that makes a message durable. The edge already bounds inbound ids to the same 128 characters, so it can only fire for a value minted inside the platform.
>
> **Link, not parent — the decision the PR should state.** The dispatch activity carries the stored context as an `ActivityLink` and starts its own trace. A job execution drains a batch belonging to N different requests, so it cannot honestly be a child of any one of them, and a true continuation makes traces unbounded in time. The correlation **id** in the logs is what delivers the cheap one-query answer; the link is what lets Jaeger navigate. `MessageDispatchScope` documents the one-line change that reverses the trade, and `Begin_Should_StartANewTrace_RatherThanContinueTheStoredOne` is what fails if someone makes it by accident.

**Goal:** the correlation id and the trace survive the two **database** handoffs, so "show me every log line about this order" and "open the trace for this order" are true for the *asynchronous* half of a flow — the half where the interesting failures live — and not only for the synchronous request.

**Why this is a milestone and not a footnote to D.** D correlates HTTP. A cross-service flow is three legs, and D covers one of them:

| Leg | Trace | Correlation id in Seq |
|---|---|---|
| Client → Gateway → service → DB (the request) | one trace | ✅ D |
| `ProcessOutboxJob` → publish → RabbitMQ → consumer → `inbox_messages` | **a new root trace** — the Quartz job runs seconds later with no ambient `Activity` | ❌ nothing |
| `ProcessInboxJob` → `IIntegrationEventHandler` → local command | **a third trace** | ❌ nothing |

The broker hop is *not* the problem — MassTransit propagates `traceparent` and §5's test pins it. The breaks are where a message waits in a table. And because `UseRequestCorrelation` is HTTP-scoped, the two async legs carry **no** `TraceId`, `SpanId` or `CorrelationId` at all today: the only property they log is `Module`, from `RequestLoggingPipelineBehavior`. So a support agent holding a correlation id can answer "was the order placed?" and nothing about the confirmation email that never arrived, the delivery never assigned, or the dashboard row that never appeared. `FoodDelivery_ProjectPlan.md` states the requirement as *"add correlation IDs to all log entries (so you can search for all logs related to one order)"* — D delivers the first half of that sentence, G delivers the parenthetical.

**Tasks:**
- **Capture.** Add a scoped `CorrelationContext` (`Common.Presentation/Correlation`, next to the middleware that owns the id — pure BCL: the id plus the request's `traceparent` string), registered by `AddHostTelemetry` alongside `HostServiceName` and populated by `CorrelationIdMiddleware`. `Common.Infrastructure` already references `Common.Presentation` (Milestone A), so the outbox interceptor can read it without a new dependency edge; nothing in an Application project needs to see it, because every writer and reader here is Infrastructure. When nothing populated it — work that *originates* in a background job — fall back to `Activity.Current`, so a job-initiated flow still gets an id rather than a null column.
- **Persist.** Add nullable `correlation_id` and `trace_parent` columns to `outbox_messages` and `inbox_messages`, stamped by `InsertOutboxMessagesInterceptor` and by `IntegrationEventConsumer`. **Columns, not a field inside the serialized `content`**: the content is the event contract, re-shaping it would touch consumers, and a queryable column also answers "which outbox rows belong to this correlation id?" — a support question in its own right. Nullable keeps the migration trivial and lets pre-existing rows dispatch unchanged. **Scope check: 11 tables across 6 databases** — Users, Orders, Restaurants, Notifications and Delivery have both tables; RealTime has `inbox_messages` only. That is 6 migrations, and it is most of this milestone's size.
- **Restore.** On dispatch, each job pushes `CorrelationId` into the Serilog `LogContext` for the duration of *that message* and starts an activity carrying the stored context. **Put the restore in one shared helper in `Common.Infrastructure`** and call it from the jobs — `ProcessOutboxJob`/`ProcessInboxJob` are copy-pasted per module (11 files), which is the same duplication D just removed from the middleware; do not write the logic 11 times.
- **Choose link, not parent — and know what you are trading.** The recommendation is that the per-message dispatch activity carries the stored context as an **`ActivityLink`** with no remote parent: a job execution drains a batch of messages belonging to N different requests, so it cannot honestly be a child of any one of them, and a true continuation makes traces unbounded in time (a message that fails and retries for an hour keeps appending to a trace whose root span "lasted" an hour). The correlation **id** in the logs is what delivers the cheap one-query answer; the link is what lets a trace UI navigate. *If the goal is instead a single end-to-end waterfall in Jaeger, this is a one-line change* — pass the parsed `ActivityContext` as the parent instead of as a link — and it is worth stating in the PR which was chosen and why, because the two look identical in code and very different in a trace UI.
- **Carry the id over the bus explicitly.** A MassTransit publish filter puts the id on a message header and a consume filter reads it back into the scoped context, so `IntegrationEventConsumer` writes it onto the inbox row. Use a header rather than MassTransit's envelope `CorrelationId`, which is a `Guid` and cannot hold an inbound client id. The trace context needs nothing here — the OTel instrumentation already carries `traceparent`.
- **Business ids on async log lines (the cheap win).** The route-derived enrichment from D cannot fire on a job, so while the scope is open also push the aggregate id the message already carries. That is what makes `OrderId = '…'` in Seq return the placement request *and* the outbox dispatch *and* the consumer's handler — the actual thing "search for all logs related to one order" means.

**Unit tests** (`Common.UnitTests`): the middleware populates the scoped context, and it falls back to the ambient activity when no request populated it; the restore helper opens a scope containing the stored `CorrelationId` and produces an activity linked to the stored context; a **null or malformed `trace_parent` degrades to no link with the id still restored** (the pre-migration-row case, which must never throw inside a job loop).

**Integration tests** (`Orders.IntegrationTests`, reusing the in-memory Serilog sink and span exporters D added): place an order with a known inbound `X-Correlation-Id`, wait for the outbox row to be processed, and assert the **outbox dispatch's** log events carry that same id and the order's `OrderId`; on the Users → Orders path, assert the **inbox dispatch's** log events carry the id the producing request started with. Add one span assertion — the dispatch activity references the originating trace — so the link survives a refactor.

**Done when:** all three legs of a cross-service flow share one correlation id in Seq, the async spans reference the trace that caused them, a pre-migration outbox row still dispatches, and existing suites stay green. ✅ **Met 2026-08-04 — see the status note at the top of this section for what shipped and where it differs.**
